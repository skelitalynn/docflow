# 实时协作模块测试方案

本文档在原测试方案基础上补充了业务逻辑与代码实现梳理，并明确每个测试的目的与原因，帮助理解“为什么要这样测试”。

------

## 1. 业务逻辑与代码实现概览（结合实现）

### 1.1 实时协作（WebSocket）
- **连接鉴权**：WS 连接携带 token（Header 或 `?token=`），由拦截器校验用户。  
- **presence 在线成员**：`presence.join/leave/ping` 维护在线列表（内存），心跳超时清理。  
- **光标同步**：`cursor.update` 上报行/列，服务端广播光标列表。  
- **实时编辑广播**：`doc.edit` 只做事件广播，不落库；真正持久化靠 REST `PUT /docs/{id}`，保存成功后广播 `doc.sync`。  
- **权限**：Viewer 可加入 presence；Editor 才能发 `doc.edit`/`cursor.update`。  

### 1.2 评论与批注
- **行内评论/批注**：通过 `blockId/paragraphIndex` 锚点定位（避免字符级漂移）。  
- **回复**：回复归属同一线程（`thread_id`）。  
- **@提及**：保存 mention 关系并触发通知。  

### 1.3 任务分配与跟踪
- **任务创建**：绑定文档、可指派负责人、可设置截止日期。  
- **任务状态**：TODO / IN_PROGRESS / DONE；DONE 时记录完成时间。  
- **任务通知**：分配与完成分别触发通知。  

### 1.4 通知
- **落库 + 推送**：通知先写表，再通过 WS 推送 `notification.push`。  
- **类型**：分享/评论/提及/任务分配/任务完成。  

### 1.5 核心约束
- ACL 是所有入口的硬校验；测试必须覆盖“有权限/无权限”。  
- WS 事件是“协作感”，数据库是“最终事实”；所以测试需要区分“广播事件”和“落库结果”。

## 5. 增量迁移执行步骤（保留数据）

如果尚未迁移，执行如下 SQL（Docker 容器示例）：

```powershell
@'
USE docflow;

CREATE TABLE IF NOT EXISTS t_task (
  task_id BIGINT NOT NULL AUTO_INCREMENT,
  doc_id BIGINT NOT NULL,
  creator_id BIGINT NOT NULL,
  assignee_id BIGINT NULL,
  title VARCHAR(200) NOT NULL,
  description LONGTEXT NULL,
  status TINYINT NOT NULL,
  due_at DATETIME NULL,
  completed_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (task_id),
  KEY idx_task_doc (doc_id),
  KEY idx_task_assignee (assignee_id),
  CONSTRAINT fk_task_doc FOREIGN KEY (doc_id) REFERENCES t_document(doc_id),
  CONSTRAINT fk_task_creator FOREIGN KEY (creator_id) REFERENCES t_user(user_id),
  CONSTRAINT fk_task_assignee FOREIGN KEY (assignee_id) REFERENCES t_user(user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

SET @col_exists := (
  SELECT COUNT(*)
  FROM INFORMATION_SCHEMA.COLUMNS
  WHERE TABLE_SCHEMA = 'docflow'
    AND TABLE_NAME = 't_notification'
    AND COLUMN_NAME = 'task_id'
);

SET @sql := IF(@col_exists = 0,
  'ALTER TABLE t_notification ADD COLUMN task_id BIGINT NULL',
  'SELECT \"task_id exists\"'
);

PREPARE stmt FROM @sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;

SET @idx_exists := (
  SELECT COUNT(*)
  FROM INFORMATION_SCHEMA.STATISTICS
  WHERE TABLE_SCHEMA = 'docflow'
    AND TABLE_NAME = 't_notification'
    AND INDEX_NAME = 'idx_notification_task'
);
SET @sql := IF(@idx_exists = 0,
  'CREATE INDEX idx_notification_task ON t_notification(task_id)',
  'SELECT \"idx_notification_task exists\"'
);
PREPARE stmt FROM @sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;

SET @fk_exists := (
  SELECT COUNT(*)
  FROM INFORMATION_SCHEMA.TABLE_CONSTRAINTS
  WHERE CONSTRAINT_SCHEMA = 'docflow'
    AND TABLE_NAME = 't_notification'
    AND CONSTRAINT_NAME = 'fk_notification_task'
);
SET @sql := IF(@fk_exists = 0,
  'ALTER TABLE t_notification ADD CONSTRAINT fk_notification_task FOREIGN KEY (task_id) REFERENCES t_task(task_id)',
  'SELECT \"fk_notification_task exists\"'
);
PREPARE stmt FROM @sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;
'@ | docker exec -i docflow-mysql mysql -uroot -pdocflow123
```

## 6. 测试用例（含为什么要测）

### 6.1 实时编辑与同步（WebSocket）

使用 Postman 或 WebSocket 客户端建立两条连接：

- A 连接：`ws://localhost:8080/ws?token={{tokenA}}`
- B 连接：`ws://localhost:8080/ws?token={{tokenB}}`

#### TC-01 presence 加入与在线列表
步骤：  
1) A 发送：
```json
{"type":"presence.join","data":{"docId":{{docId}}}}
```
2) B 发送同样消息。  

期望：A/B 都收到 `presence.join`，`members` 包含双方。  
为什么要测：presence 是协作感基础，需验证 WS 广播与在线成员合并逻辑。

步骤：

期望：  
- B 收到 `doc.edit`，内容展示更新。  
- REST 保存后，B 可收到 `doc.sync` 或 `GET /docs/{id}` 获取最新内容。  
为什么要测：`doc.edit` 只广播，不落库，必须区分“事件同步”与“最终存储”。

#### TC-04 无权限编辑阻断
步骤：  
1) 将 B 权限改为 Viewer。  
2) B 发送 `cursor.update` / `doc.edit`。  

期望：不会广播（A 未收到事件）。  
为什么要测：防止 Viewer 篡改协作状态，验证 ACL 强校验。  

#### TC-05 leave / 断线
步骤：  
1) B 断开 WS 或发送：
```json
{"type":"presence.leave"}
```
2) 观察 A 收到 `presence.leave`。  

期望：在线成员更新。  
为什么要测：离线清理是协作一致性的关键，否则会出现“幽灵在线”。

## 7. 验收要点

- WebSocket 广播可被多端接收（presence / cursor / doc.edit）
- 评论支持锚点定位（blockId / paragraphIndex）
- @ 提及触发通知
- 任务分配/完成通知可追溯

------

## 8. 常见问题

- WS 连接 401：检查 token 是否有效，建议使用 `?token=...` 方式连接。
- 编辑广播无回包：确认使用 Editor 权限，Viewer 发送不会广播。
- 通知未出现：检查 `t_notification` 是否已迁移并确认 `/notifications` 可访问。
